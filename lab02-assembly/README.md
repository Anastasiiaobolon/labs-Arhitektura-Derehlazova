# Lab 2. Від C до Assembly та машинного коду

**Середовище:** GitHub Codespaces, Ubuntu, GCC, GNU Binutils (`objdump`). Assembly у **Intel syntax** (`-masm=intel`).
Згенеровані `.s` файли та executable в репозиторій не додаються: вони відтворюються командами нижче.

## Файли

`arithmetic.c`, `operations.c`, `condition.c`, `loop.c`, `optimize.c`, `analyze.c`

## Підготовка. `arithmetic.c`

```bash
gcc -Wall -Wextra arithmetic.c -o arithmetic && ./arithmetic
```
```text
Result: 12
```

**Як CPU виконає `int result = a + b;` (словами):** взяти значення `a` з пам'яті в регістр, взяти значення `b`, додати їх, записати суму в змінну `result`.

## Завдання 1. Assembly з C (`-S`)

```bash
gcc -Wall -Wextra -O0 -S arithmetic.c -o arithmetic.s
gcc -Wall -Wextra -O0 -S -masm=intel arithmetic.c -o arithmetic_intel.s
```
Прапорець `-S` зупиняє GCC на етапі Assembly (текстовий файл), `-O0` вимикає оптимізацію, `-masm=intel` вмикає Intel-синтаксис.

У `arithmetic_intel.s` знайдено: мітку `main:`, інструкції `mov` (запис 5 і 7 у змінні), `add` (додавання), `call printf@PLT`, `ret`.

- **Чи кожному рядку C відповідає одна інструкція?** Ні, одному рядку може відповідати кілька інструкцій (завантаження, дія, збереження).
- **Чи є в Assembly змінні `a`, `b`, `result`?** Ні, імен немає. Змінні замінені адресами на стеку типу `DWORD PTR -4[rbp]` та регістрами.
- **Скільки інструкцій у тілі `main()`?** `19` (разом із prologue/epilogue).
- **Чи є додавання?** Так, інструкція `add`.

## Завдання 2. Арифметична операція (`operations.c`)

```bash
gcc -Wall -Wextra -O0 operations.c -o operations && ./operations   # 30
gcc -Wall -Wextra -O0 -S -masm=intel operations.c -o operations.s
```
У `calculate:` аргументи `a` та `b` приходять у регістрах `edi`, `esi`, зберігаються на стеку, потім завантажуються в `edx` і `eax`, і `add eax, edx` обчислює суму. Результат лишається в `eax`.

| C | Основна Assembly-інструкція |
|---|---|
| `a + b` | `add` |
| `a - b` | `sub` |
| `a * b` | `imul` |

**Що змінилося в Assembly після зміни операції в C?** Змінилася лише одна інструкція арифметики (`add` → `sub` → `imul`). Решта коду (збереження аргументів, завантаження в регістри, повернення в `eax`) така сама.

## Завдання 3. `if` (`condition.c`)

```bash
gcc -Wall -Wextra -O0 condition.c -o condition && ./condition   # 20
gcc -Wall -Wextra -O0 -S -masm=intel condition.c -o condition.s
```
У `max_value:` є `cmp eax, DWORD PTR ...` (порівняння `a` і `b`) та умовний перехід `jle` (jump if less or equal). Дві гілки виконання: або виконується `return a`, потім `jmp` на вихід, або перехід `jle` веде на мітку з `return b`.

```text
C                      Assembly
if (a > b)       →     cmp ... ; jle .L2
return a         →     mov eax, <a> ; jmp .L3
else             →     мітка .L2:
return b         →     mov eax, <b>
```

**Чи існує інструкція `IF`?** Ні. На рівні CPU є лише порівняння (`cmp`, яке виставляє прапорці процесора) та умовні переходи (`jle`, `jg`, `je`...), які залежно від прапорців або стрибають на іншу адресу, або продовжують виконання далі. `if` реалізується комбінацією `cmp` + умовний `jmp`.

## Завдання 4. Цикл (`loop.c`)

```bash
gcc -Wall -Wextra -O0 loop.c -o loop && ./loop   # 15
gcc -Wall -Wextra -O0 -S -masm=intel loop.c -o loop.s
```
Структура циклу в `sum_to:`: початкові значення (`sum = 0`, `i = 1`) → `jmp` на перевірку умови → тіло (`sum += i`, `i++` через `add`) → `cmp` `i` з `n` → `jle` назад на початок тіла, якщо умова істинна.

- **Яка інструкція порівнює?** `cmp`.
- **Яка реалізує перехід?** `jle` (умовний) та `jmp` (безумовний, на початку).
- **Чи є поняття `for` в Assembly?** Ні, лише мітки, `cmp` і переходи.
- **Як CPU визначає, що цикл треба повторити?** `cmp` виставляє прапорці; якщо умова виконується, `jle` стрибає назад на тіло, інакше виконується наступна інструкція після циклу.

## Завдання 5. Виклик функції

У `main:` є `call calculate` (передаються аргументи 10 і 20 через `edi`, `esi`). Код `calculate` починається з мітки `calculate:`, завершується інструкцією `ret`. Результат повертається в регістрі **`eax`**.

**Чому після `call` CPU має знати, куди повертатися?** `call` кладе адресу наступної інструкції (return address) на стек, а `ret` бере її зі стека і стрибає назад. Без цього функція не знала б, звідки її викликали (детальніше про стек у Lab 3).

## Завдання 6–7. Machine code (`objdump`)

```bash
gcc -Wall -Wextra -O0 operations.c -o operations
objdump -d -M intel operations | grep -A12 "<calculate>:"
```

Вставте три рядки **зі свого** виводу (адреса, байти, Assembly):

| Address | Machine-code bytes | Assembly |
|---|---|---|
| `114d` | `55` | `push rbp` |
| `114e` | `48 89 e5` | `mov rbp, rsp` |
| `115d` | `01 d0` | `add eax, edx` |

(Для `add eax, edx` очікується `01 d0`, але адреси та точні байти перевірте у себе.)

- **Що зберігається у виконуваному файлі?** Machine code (байти). Assembly як текст там відсутній.
- **Навіщо `objdump` показує Assembly?** Він **дизасемблює** байти назад у зручний для людини запис.
- **Чи мають усі інструкції x86-64 однакову довжину?** Ні, довжина змінна (наприклад, `push rbp` це 1 байт, `mov rbp, rsp` це 3 байти).
- **Чому людині зручніше Assembly?** Мнемоніки (`add`, `mov`) легше читати, ніж шістнадцяткові байти.

## Завдання 8. `-O0` та `-O2`

```bash
gcc -O0 -S -masm=intel operations.c -o operations_O0.s
gcc -O2 -S -masm=intel operations.c -o operations_O2.s
diff -u operations_O0.s operations_O2.s
```
При `-O2` компілятор використовує регістри замість пам'яті, прибирає зайві збереження на стек та prologue/epilogue, може вбудувати (inline) `calculate()` у `main` без `call`, а іноді навіть обчислити `10 + 20` під час компіляції. Тому один C-код не має єдиного незмінного Assembly.

**Мій висновок з вашого diff:** `при `-O2` функція `calculate` скоротилася з 12 інструкцій до 3 (`endbr64`, `lea`, `ret`): зникли prologue/epilogue (`push rbp`, `mov rbp, rsp`, `pop rbp`) та всі звернення до стека, а додавання виконується в регістрах однією інструкцією `lea eax, [rdi+rsi]`. У `main` компілятор взагалі прибрав виклик `calculate` і одразу підставив готове значення 30 (`mov edx, 30`), тому результат програми той самий, а код коротший.`

## Завдання 9. Прогноз компілятора (`optimize.c`)

**Прогноз:** варіант B, оптимізуючий компілятор одразу поверне `30`.

```bash
gcc -O0 -S -masm=intel optimize.c -o optimize_O0.s
gcc -O2 -S -masm=intel optimize.c -o optimize_O2.s
```
- `-O0`: функція `answer` має prologue (`push rbp`, `mov rbp, rsp`), `mov eax, 30`, `pop rbp`, `ret`. Навіть без оптимізації `10 + 20` згорнуто в `30`, додавання під час виконання немає.
- `-O2`: лишається `mov eax, 30` + `ret` (prologue прибрано). У `main` виклик `answer()` також може бути вбудований.

**Чому компілятор має право замінити `10 + 20` на `30`?** Результат відомий на етапі компіляції й не залежить від виконання. Спостережувана поведінка програми не змінюється (правило *as-if*), тому така заміна допустима і дає швидший код.

## Фінальне завдання. `analyze.c`

Функція `analyze(int a, int b)`: порівнює `a` і `b` (if/else), виконує віднімання або додавання, потім 3 рази множить результат на 2 у циклі та повертає його.

```bash
gcc -Wall -Wextra -O0 analyze.c -o analyze && ./analyze      # 48 та 88
gcc -Wall -Wextra -O0 -S -masm=intel analyze.c -o analyze.s
objdump -d -M intel analyze
```

Знайдені у дизасемблюванні `analyze`:
- арифметика: `sub` / `add` та множення на 2 (`add eax, eax` або `sal`/`shl`)
- comparison: `cmp`
- conditional jump: `jle`
- цикл: `cmp` + `jle` назад
- виклик: `call` (з `main`)
- повернення: `ret`

Три інструкції з **мого** executable:

| C construct | Assembly | Machine-code bytes |
|---|---|---|
| `a > b` | `cmp eax,DWORD PTR [rbp-0x18]` | `3b 45 e8` |
| `result = a - b` | `sub eax,DWORD PTR [rbp-0x18]` | ` 2b 45 e8` |
| `return result` | `ret` | `c3` |

## Відповіді на контрольні питання

- **ISA** (Instruction Set Architecture): специфікація набору інструкцій процесора, їх кодування та регістрів (наприклад, x86-64).
- **Чому CPU не виконує C?** CPU розуміє лише машинні інструкції своєї ISA, а C потрібно спершу скомпілювати.
- **Assembly та machine code:** Assembly це текстовий запис інструкцій, machine code це їхнє бінарне кодування.
- **`-S`:** зупиняє компіляцію після генерації Assembly.
- **Навіщо `-O0`:** вимикає оптимізацію, і Assembly точніше відповідає C-коду.
- **Operand:** значення або місце (регістр, пам'ять, число), з яким працює інструкція.
- **`mov`:** копіює значення між регістром, пам'яттю та числом.
- **`cmp`:** порівнює два значення й виставляє прапорці процесора для наступного умовного переходу.
- **`if` на рівні машини:** `cmp` + умовний перехід.
- **Цикл:** умовний перехід назад на початок тіла.
- **`call`:** викликає функцію і зберігає адресу повернення.
- **`ret`:** повертає виконання на збережену адресу повернення.
- **Чому один рядок C ≠ одна інструкція:** рядок може розкладатися на кілька кроків (завантаження, дія, збереження) або взагалі зникнути після оптимізації.
- **`objdump -d`:** дизасемблює машинний код у Assembly, показуючи адреси та байти.
- **Чому `-O0` і `-O2` відрізняються:** оптимізатор прибирає зайве, використовує регістри, робить inlining.
- **Чи може компілятор видалити код?** Так, якщо це не змінює спостережуваної поведінки (мертвий код, обчислення, результат яких не використовується, константні вирази).

## Висновок

Шлях C → Assembly → machine code підтверджено експериментально. Арифметика, `if`, цикл та виклик функції зводяться до `add/sub/imul`, `cmp` + умовних переходів та `call/ret`. Executable містить байти, а не текст Assembly; `objdump` показує їхній дизасембльований вигляд. Assembly залежить від рівня оптимізації та версії GCC.
